# Identity
- An identity lives server-side (`private.identities`). Each device is an auth session mapped to it (`private.identity_sessions`), so many devices can share one identity. Nothing depends on the original auth user, so Supabase cleaning up old anonymous users can't delete an identity.
- **Linking (0006):** the new device creates a one-time code (128 bits, hash stored, valid 5 minutes, 5 tries) and shows it as a QR/link. The existing device opens the link (its normal camera works) and approves. The new device then completes and takes the identity. A device that already has its own posts is refused, so content is never orphaned.
- **Recovery:** the app generates a 125-bit code on the device. Only sha256 of it is sent, and the server stores a hash of that hash, so neither a database leak nor the server ever holds the code. Recovery is limited to 5 wrong tries per hour.
- **Devices:** listed with a label. Removing one detaches its session immediately. A removed or purged device that keeps using the app simply becomes a new anonymous identity.
- **Purge this device:** detaches the session and wipes local storage. **Delete identity:** deletes content and closes the identity on every device.
- **Design decision:** device signing keys are not created yet. The spec's key pair only matters once DMs are end-to-end encrypted, and nothing would use it today. Linking authorises through the approving device's session plus the one-time code, so no key material has to move. Add per-device keys with E2EE DMs.
- **Known limits:** on iPhone, an installed home-screen app and Safari keep separate storage, so a link opened from the camera lands in Safari and approves as whichever identity Safari has. Approve from the same place the identity lives. Losing every device without a recovery code loses the identity by design.
